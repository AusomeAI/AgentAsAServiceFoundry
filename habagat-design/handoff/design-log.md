# Design Log: Decisions and Gaps

> Per Doc 60 §3's shared preamble ("what to do when you hit a gap or a conflict") and the UI/UX Designer Agent's own task instructions ("a `handoff/design-log.md` explaining every decision you made that Doc 56 did not already specify"). Doc 56 fixed layout and philosophy; everything below is a judgment call made to fill in exact spacing, exact copy, exact color, or a genuinely unspecified interaction — recorded so a reviewer knows precisely what to check.

## Five UX decisions made beyond what Doc 56 specified

1. **The "Uncertain" block on Escalation Review is conditionally shown, not always present** ([escalation-review.md](../screens/escalation-review.md), "Uncertain block"). Doc 56 §2.2 lists it as a fixed region in the layout flow but doesn't address what happens when an escalation reason (`out_of_policy`, `budget_exhausted`) genuinely has nothing for the agent to be "uncertain" about. I chose to collapse the region entirely in those cases rather than show it empty or with filler text ("Nothing to report"), on the reasoning that an empty region between Evidence and Actions would read as a layout defect, and filler text would train reviewers to skim past a region that's sometimes meaningless. **Check:** confirm with a real reviewer cohort that the layout doesn't feel unstable when this region appears/disappears across different escalations in the same session.

2. **Button radius uses `radii.md`, not `radii.full`**, reserving fully-rounded pills for status badges/chips only ([base.tokens.json](../tokens/base.tokens.json) `radii` comment). Doc 56 says nothing about corner radius. I made this choice specifically so a reviewer's eye distinguishes "this is an action" (rectangular-ish, `md`) from "this is a status/label" (pill, `full`) purely by shape, reinforcing the semantic-vs-accent color separation Doc 56 §5.2 already asks for in a different dimension (shape now carries a second, independent signal). **Check:** this is a house-style choice with no functional consequence; low risk, but confirm it doesn't fight an existing Habagat brand guideline if one exists outside this corpus.

3. **The rubber-stamping soft-nudge threshold (Doc 56 §2.5, "unusually low median dwell time") is implemented as a literal minimum-dwell gate on the action buttons** (a fixed ~4 seconds before Approve/Modify/Reject become interactive), not purely as a passive telemetry signal. Doc 56 §2.5 describes tracking dwell time as a *quality signal to the team lead*, not a *blocking gate* — I added the blocking gate as the mechanism that makes "the evidence panel has been scrolled into view or a minimum dwell time has passed" (Doc 56 §2.5's own sentence) concrete, since that sentence already implies *some* gating mechanism exists before the buttons activate; I chose dwell time as the simpler of the two conditions to implement first. **Check:** this is exactly the open question Doc 56 §198 item 2 already flags as needing real usage data — treat my 4-second figure as a placeholder, not a validated number, and instrument it from day one so it can be tuned.

4. **The "Uncertain" block's background treatment is a diluted warning tint, not a full `semantic.warning-bg`** ([escalation-review.md](../screens/escalation-review.md) region spec). I judged that using the full-strength warning color here would visually compete with the Evidence Panel's own `diff.added-bg`/`diff.removed-bg` treatment for "the thing that actually needs your attention" — the evidence panel's discrepancy highlighting should read as more urgent than the agent's own stated uncertainty, since the discrepancy is the fact and the uncertainty is the agent's self-assessment. **Check:** this requires an actual reduced-opacity or lightened warning token to be added to the token files at implementation time — I did not add a formal `semantic.warning-bg-subtle` token, which is itself a gap; the engineer should either add one (cleanest) or apply an opacity modifier at render time (acceptable, but breaks the "every color from a token" acceptance criterion in component-contracts.md — flagging this as a small follow-up token addition needed before merge).

5. **Kill Switch is not a top-level nav item** in the customer Console, reached instead via a link from Policy Control ([customer-console.md](../screens/customer-console.md), "Cross-screen navigation"). Doc 56 §1.3's mermaid diagram does show `KILL` as a node with an incoming edge only from `POLICY`, which is what I followed literally — but Doc 33 §4 separately describes the kill switch as "immediate disable, self-service," which could argue for higher prominence (e.g., a persistent header button, given its emergency nature). I chose to follow Doc 56's diagram exactly rather than second-guess the information architecture per this document's own constraint ("never invent a new nav structure"), but flagging the tension explicitly since an emergency control being one click deeper than expected is worth a deliberate human decision, not a default I should have made unilaterally.

## Gaps found (routed per Doc 60 §6, not resolved unilaterally)

1. **No screen spec exists for tenant detail** (the destination of clicking a row in the Fleet Coordinate Matrix). Doc 56 §4.2 describes the matrix and its drill-down behavior conceptually ("with drill-down into any tenant that isn't [healthy]") but never names or specifies a tenant-detail screen. I did not invent one. **Status:** open — flagged in [handoff/component-contracts.md](./component-contracts.md) under `<FleetCoordinateMatrix />`'s "Open item." A human should decide whether this needs a follow-up design pass before the Software Engineer Agent builds the matrix's click-through target, or whether a minimal placeholder (e.g., reusing the customer Console's Overview layout, scoped to that tenant) is an acceptable interim.

2. **The Blueprint Registry Browser screen** (named in Doc 56 §4.2's information architecture diagram) has no dedicated design in this handoff. I judged this to be "a straightforward version-list-and-detail pattern with no novel interaction beyond the existing patterns in this document" (stated explicitly in [internal-operator-console.md](../screens/internal-operator-console.md)'s closing note) and did not spend design effort re-deriving a list/detail pattern the corpus's existing components (particularly the Run Explorer's list-plus-slide-over-detail pattern) already establish. **Status:** a deliberate simplification per this agent's own standards ("build the simplest thing that satisfies the stated contract... note the simplification"), not an oversight — but the Software Engineer Agent should confirm the Run Explorer pattern genuinely transfers before assuming it without a design check.

3. **No conflict found between Doc 56 and any other binding document.** The Teams card design (screens/teams-card.md) required translating Doc 56 §3.2's prose description into actual Adaptive Card v1.5 schema elements, which is new specification work (choosing `Action.ShowCard` vs `Action.Submit`, for instance) rather than a restatement — but every choice there was constrained to satisfy Doc 56's stated behavioral requirements exactly (top-3 chips, Modify always deep-links, no inline field editing), so I consider this an elaboration, not a deviation. Recorded for a reviewer to confirm the Adaptive Card schema choices are still current against whatever Teams SDK version the Software Engineer Agent actually targets (Adaptive Card schema versions do evolve).

## One accessibility token gap found during this work

`semantic.warning-bg-subtle` does not exist in the token files but is referenced conceptually in design decision #4 above. This should be added to both `customer.tokens.json` and `internal-operator.tokens.json` (a lightened/reduced-alpha variant of `semantic.warning-bg`, contrast-verified against `text.primary` at the customer theme's required ratio) before the Escalation Review screen's Uncertain block is implemented — flagged here rather than added speculatively, since the exact dilution amount should be chosen by looking at the real header/evidence-panel colors side by side, which is easier to judge once a working build exists than to guess correctly on paper.
